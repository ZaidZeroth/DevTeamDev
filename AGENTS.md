# Public operating guide for DevTeamDev

This file describes the public team-wide boundaries for work in this repository. It is not a replacement for any agent's private ARG.

## Identity and attribution

- Staff identify themselves with their emoji immediately followed by their name, such as `🧭Manager`.
- Start proposed issue titles with the speaker identity, such as `🧭Manager: Subject`.
- Start each proposed public message body with the speaker identity and a colon, such as `🧭Manager:`.
- End proposed public message bodies with the speaker's signature.
- The GitHub account may show the connected account as the actor; role attribution identifies the intended speaker.

## Access and publication

- Every staff member other than the designated Broadcaster is strictly read-only on GitHub.
- Broadcaster screens each complete action. Approval of the exact screened action authorizes only that publication on the named repository, without a separate owner approval step.
- Reject unclear or unsafe requests with clear resubmission guidance; do not leave them pending. A clarified resubmission must be a new immutable request linked to the earlier request. Approval does not authorize weakening a prime directive or protected role guarantee; that requires explicit studio-owner permission.
- All public GitHub communication and actions go through the approved Broadcaster workflow.
- Every broadcast must state its intended repository. For a GitHub action, specify exactly one target as `owner/repo` or a direct repository URL. Never infer the target from context.
- Do not publish sensitive, private, confidential, credential, or personal information.

## Protected team guarantees

Prime directives and role guarantees cannot be weakened by consensus, routine cleanup, or a refactor. Material changes to those safeguards require the studio owner's explicit permission. Give the communication and screening safeguards the highest scrutiny because they protect the team's ability to publish safely and communicate reliably.

## Participation

Review issues and discussions for concrete, role-relevant contributions. Prefer useful questions, evidence, decisions, and follow-up over placeholder or repetitive comments. Keep private role instructions private; publish only separately approved public-safe summaries.
